# Retrieval Bug — Meal Lookup Across Two Keying Schemas

**Repo:** `mlp-backend` (private)
**Commit:** `22b4652` — *Restore meal swap feature and grocery list images (#211)*
**Date:** 2026-04-25
**Files touched:** `sam-backend/src/routes/mealplan_feedback_single.py`, `sam-backend/src/utils/grocery.py`

---

## Symptom

The single-meal feedback endpoint started returning `400 Meal not found in mealplan` for a subset of users. The mealplan itself loaded fine, the user's date and meal_type were correct, and the meal was visibly present in the stored JSON — yet `_find_meal_in_mealplan()` returned `None`.

## Root cause

We had shipped a catalog-matching path that produced mealplans keyed differently from the legacy generator:

- **Legacy mealplans:** `meal_slot` is a dict keyed by `foodid` (string hash). `recipe_id` is `None` or absent inside each entry.
- **Catalog-match mealplans:** entries carry a real numeric `recipe_id` from `curated_meals`.

The lookup function only scanned by `recipe_id`, so any user whose plan was generated by the legacy path silently failed. Same class of bug as a RAG retriever that hard-codes one namespace / one ID convention while the underlying corpus has drifted to a second one.

## Fix

Make the lookup bidirectional, prefer the O(1) path, and accept either identifier on the request:

```python
def _find_meal_in_mealplan(
    mealplan_data, date, meal_type,
    foodid: Optional[str],
    recipe_id: Optional[int],
    logger,
):
    day_meals = mealplan_data.get(date)
    if not day_meals:
        return None
    meal_slot = day_meals.get(meal_type)
    if not meal_slot:
        return None

    # Fast path: direct key hit on foodid.
    if foodid is not None and foodid in meal_slot:
        meal_details = meal_slot[foodid]
        return {
            "recipe_id": meal_details.get("recipe_id"),
            "foodid": meal_details.get("foodid", foodid),
            "label": meal_details.get("label", "Unknown"),
            "ingredients": meal_details.get("ingredients", []),
            "date": date,
            "meal_type": meal_type,
        }

    # Fallback: scan by recipe_id for newer catalog-match plans.
    if recipe_id is not None:
        for key, meal_details in meal_slot.items():
            mr = meal_details.get("recipe_id")
            if mr is not None and int(mr) == recipe_id:
                return {
                    "recipe_id": recipe_id,
                    "foodid": meal_details.get("foodid", key),
                    "label": meal_details.get("label", "Unknown"),
                    "ingredients": meal_details.get("ingredients", []),
                    "date": date,
                    "meal_type": meal_type,
                }

    logger.info(
        f"Meal not found in {meal_type} on {date} "
        f"(foodid={foodid}, recipe_id={recipe_id})"
    )
    return None
```

Request parsing was also made backward-compatible — either `foodid` (string) or `recipe_id` (number) is accepted, with the error message echoing whichever identifier the caller actually sent.

## Secondary fix — grocery ingredient resolution

The same commit fixed an adjacent retrieval issue: matching an ingredient label like `"thick-cut bacon"` to the grocery row `"bacon"` was being done with exact ILIKE, which missed compound modifiers. Replaced with a scoring function that prefers suffix matches (`endswith`) over arbitrary substring hits, falling back to token overlap. Same "your matcher is too strict for the actual surface forms in the corpus" failure mode that bites Pinecone/pgvector queries when chunk normalization isn't aligned with query normalization.

## Takeaway

Two retrieval lessons that map directly to vector-DB work:

1. **Don't assume one keying scheme.** Mealplans, vector chunks, document IDs — they all drift as new generators ship. Lookups need to be schema-tolerant on read even if writes are clean.
2. **Strict matchers fail silently.** Whether it's ILIKE on a SKU or cosine on a chunk, the failure is invisible until someone reports "the right answer isn't coming back." Add the fallback path and log which path fired.
